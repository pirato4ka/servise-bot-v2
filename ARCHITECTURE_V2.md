# Architecture V2 — HelpDesk + Dynamic Admins + CRUD

## Новые требования и как я их закрыл как Senior

### 1. Диалог Админ ↔ Пользователь через Reply (Ключевое)

**Проблема прошлого подхода:** анкета улетала и терялась.

**Решение V2 — Ticket System на основе reply threading:**

```
Пользователь (бот)  --> анкета --> [Тикет #1: admin_msg_id=1024]
                                           |
Админ в админ-чате отвечает REPLY на 1024  --> бот перехватывает
       |
       +--> message.reply_to_message.message_id == 1024 ?
              Да -> ищем ticket по admin_message_id
                   -> берем user_id из тикета
                   -> bot.send_message(user_id, text, from admin)
                   |
Пользователь пишет еще что-то --> бот форвардит в админ-чат как reply к 1024
                                     (чтобы у админа был тред диалога)
```

**Технически:**
- Таблица `tickets (user_id, admin_message_id, admin_chat_id, status)`
- Handler `admin_reply_handler.py`: слушает ТОЛЬКО сообщения в ADMIN_CHAT_ID где `F.reply_to_message`
- Проверяет: `admin_message_id` есть в БД? Если да — это ответ клиенту.
- Поддержка медиа: text, photo, voice, document — через `copy_message` или `send_*`
- Ответ пользователю приходит **от имени бота** (важно для анонимности админа), но с пометкой `💬 Відповідь від адміністрації:`

### 2. Продолжение диалога
После закрытия анкеты FSM очищается. Любое следующее сообщение пользователя (не команда) попадает в `user_chat.py`:

- Если есть открытый тикет — форвард в админ-чат как `↩️ Продовження діалогу` reply к исходному сообщению.
- Если нет — создает новый тикет "Вільне повідомлення".

### 3. Источник вступления (Канал)
Реализуем через deep-link: `t.me/your_bot?start=channel_xyz` или `?start=cpa_123`

В `start.py`:
```python
args = message.text.split() # /start channel_xyz
source = args[1] if len>1 else "direct"
```
Сохраняем в `users.source`. 

В приветственном сообщении:
```
🔗 Джерело: Канал @channel_xyz
```
И в админ-уведомлении тоже. Это закрывает требование "указывает источник отправки".

Если юзер реально вступил в канал где стоит бот — ловим `chat_member` event (бот должен быть админом канала).

### 4. Динамические права администратора
Требование: "всем пользователям, добавленным в админский чат — выдать права".

**Реализация:**
- Таблица `admins (user_id, added_at)`
- Handler `membership.py`:
  - `ContentType.NEW_CHAT_MEMBERS` в админ-чате -> add to DB
  - `ContentType.LEFT_CHAT_MEMBER` -> remove
  - `ChatMemberUpdated` filter для ADMIN_CHAT_ID -> отслеживаем `member` -> `administrator/member`
  - Bootstrapping: при старте бота делаем `get_chat_administrators(ADMIN_CHAT_ID)` и `get_chat_members` (если возможно) — сидируем таблицу.
  - Middleware `is_admin` проверяет: `user_id in admins OR user_id in cached_admins`

Любой кто пишет в админ-чате автоматически становится админом (если его еще нет) — защита от рассинхрона.

### 5. Админ-панель — CRUD услуг + Статистика

Теперь услуги не в .py файле, а в БД `services` (SQLite). Это позволяет CRUD без редеплоя.

**Панель вызывается:**
- В админ-чате: `/admin`
- В личке админа: `/admin` (проверка прав)

**Меню `/admin`:**
```
🛡️ Адмін-панель

[ 📊 Статистика ] [ 🛠 Послуги ]
[ 👥 Адміни ]     [ 📢 Розсилка (опц) ]
```

**CRUD Послуг:**
- Список: пагинация, каждая услуга -> кнопки `✏️ Редагувати` `❌ Видалити` `👁 Вкл/Выкл`
- Добавить: FSM `AddService` — 5 шагов:
  1. ID (латиницей)
  2. Emoji
  3. Название для кнопки
  4. Краткое описание
  5. Полные условия (HTML)
- Редактировать: тот же FSM, но с предзаполнением
- Вкл/Выкл: is_active

**Статистика:**
- `/stats` показывает:
  - Всего пользователей: 152
  - Сегодня: 12
  - Активных диалогов: 5
  - Топ-услуга: VIP
- Кнопка `👤 Список користувачів` -> пагинация с карточкой каждого:
  ```
  ID: 123456
  @username
  Ім'я з анкети: ...
  Вік, дата, послуга, source, first_seen
  [Заблокувати] [Написати]
  ```

### 7. Безопасность
- Админ-ID не светится юзеру
- Все ответы идут от имени бота
- SQLite с WAL режимом
- Антифлуд 1.5 сек для юзеров, для админов — безлимит
- Логи без персональных данных
